Hostel Hunt

A hostel and PG booking platform for Hyderabad

  • Pre-launch, on staging
  • Solo project

Students find a bed, reserve it and pay rent in one app. Owners manage rooms, bookings and dues in a web dashboard. I designed and built the backend, the dashboard and the mobile app myself.

Project summary

Problem, solution and my contribution

Problem
Finding a bed in a hostel or PG, reserving it and paying rent usually takes several separate steps, and owners have to keep track of who has booked and who has paid.
Solution
One platform with three connected parts: a Flutter app for students, a Next.js dashboard for owners, and a Django REST API with a PostgreSQL database behind both.
My contribution
I built all three parts: the API and data model, login with email OTP and JWT, bed booking, sandbox payments with Razorpay, background jobs, the admin dashboard, the mobile app, automated tests and the deployment pipeline.
Technology
Python 3.13, Django 5.2, Django REST Framework, PostgreSQL on Supabase, SimpleJWT, Razorpay (sandbox), Cloudinary, Next.js 16, React 19, TypeScript, Tailwind CSS, Flutter, Dart, Riverpod, GitHub Actions, Render, Sentry.
Current status
Running on staging and installed on test devices. Payments work in sandbox mode only. The newest rent and stay features are on separate branches that are not merged into main yet.

Technical challenges

Problems I had to solve, and how

Reserving a bed safely

Two students must never get the same bed. Booking uses database row locks (select_for_update with SKIP LOCKED) and holds that expire if the student does not pay. Tests cover two students competing for one bed.

Login and OTP

Students sign in with an email one-time code, and the API issues JWT tokens that can be refreshed and revoked. Requests are rate limited, and tests check that the code is never exposed in a response.

Payments that can be repeated safely

Razorpay sends the same webhook more than once. The API verifies the signature, confirms each payment only once, reconciles mismatches and includes a replay tool for testing.

Sandbox mode only. No live payments.

Keeping owners’ data separate

Each owner may only see their own hostels. Scoping is applied in queries, in object lookups and when validating input, and a Django check flags any model that is not scoped.

Background jobs without a message broker

Reminders and cleanup run from a PostgreSQL outbox processed by cron workers, with retries, backoff and duplicate protection. The job is saved in the same transaction as the change that caused it.

API contracts and database changes

The API is versioned under /api/v1 with generated OpenAPI documentation and contract tests. The database uses UUID keys, constraints, indexes and about 40 migrations on the latest branch.

Testing and quality assurance

How the code is checked

  • GitHub Actions runs the backend checks on every change, using PostgreSQL 16 and Redis 7 service containers.
  • Staging-only Locust load tests with pass and fail thresholds.
  • Sentry monitors errors in the backend and the Flutter app, and the API has a /healthz endpoint.
  • Daily database backups, encrypted with age and kept for 30 days.

Status and lessons learned

Where the project stands

What debugging taught me

  • A missing booking ID in an API response broke the payment flow. Fixing it showed me why API contracts need tests.
  • A Django secret key appeared in server logs. I rotated it and changed how environment variables are handled.
  • Login state was lost in some app flows, which I fixed and covered with tests.

What is still to do

  • Launch the app on the Play Store.
  • Test payments end to end on staging before using live mode.
  • Merge the rent and stay branches into main.
  • Host the owner dashboard. The mobile app is the priority.
